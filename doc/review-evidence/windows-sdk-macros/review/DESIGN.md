# Windows SDK repair design review

Reviewer: delegated `/root/sdk_repair_design_review`, 4 November 2026. Immutable source `107efc934847f57ecb16a6b1d204a94eed5d8df2`, existing native artifacts only. No compiler, test, native job, external API, source modification or publication was performed. Parent BTX test 1 (2) owns implementation and qualification. This report is the sole reserved output.

## Strongest counterexample and decision

**A repair confined to `compat/compat.h` does not close the second cleanup boundary in `compat/mingw/posix_extra.h`.** The latter independently removes both lowercase macros and is privately force-included for Windows `bitcoin_modelnet` objects (`src/modelnet/CMakeLists.txt:2567–2573`). Some identifier-bearing modelnet files do not need to include ordinary compat themselves. A successful ordinary socket/args/netif campaign therefore cannot establish the modelnet boundary or all supported Windows profiles.

**Prefer A: preserve the flat Windows SDK meaning of uppercase `FAR`/`NEAR` as empty replacements before undefining lowercase `far`/`near`, at both existing cleanup sites.** Retain the current identifier cleanup and all unrelated macro handling. This repairs the dependency that was actually demonstrated, without renaming application variables or eagerly importing a growing list of SDK headers. The recommendation is a coherent candidate, not a tested product verdict.

The relevant invariant is simultaneously:

1. SDK declarations and delayed SDK macros still see empty `FAR` and `NEAR` after either BTX cleanup boundary.
2. Application identifiers spelled `near` and `far` remain ordinary C++ identifiers after that boundary, including after the supported late SDK includes.
3. Header order and subsequent includes do not reintroduce a dependency from uppercase aliases onto removed lowercase macros.

For the inspected native SDK, replacing each alias with an empty object-like macro preserves its effective expansion before cleanup. The recorded `shared/minwindef.h` has `#define far` and `#define near` at 94–95, then `#define FAR far` / `#define NEAR near` at 150–151. `um/winsock2.h` retains `FAR` in FD_SET/FD_ZERO/FD_ISSET replacement lists at 158/173/175. Redefinition must therefore occur while repairing this common alias boundary, rather than by patching each FD macro.

A straightforward implementation is an explanatory comment followed by `#undef FAR`, `#define FAR`, `#undef NEAR`, `#define NEAR` within each header's existing Windows guard, immediately before the existing lowercase cleanup. Explicit undef avoids a macro-redefinition diagnostic. This deliberately chooses the known empty flat-Windows meaning; it is not an attempt to generically capture a macro's expansion with another macro definition. In particular, defining a new alias to `far` before undefining `far` would reproduce the original defect because macro replacement is deferred.

## Alternatives and limits

**B, retain SDK macros and rename BTX identifiers, can be coherent only as a wider change.** It must remove both cleanup sites, inventory production and test identifier uses and update matching declarations/definitions. Merely removing the ordinary compat undef statements is already contradicted by native identifier controls and `net_processing.cpp:9678,9687` (`const bool near`, `if (!near)`). Current modelnet witnesses include the public declaration/definition of `SwarmNeighbors(..., int near, ...)` at `swarm_lifecycle.h:26` and `.cpp:145,156–180`, plus both local iterators at `swarm_execnbhd/seating.cpp:63–69`. Retaining the macros in ordinary compat while leaving posix_extra cleanup makes behavior depend on which target compiles the same header. B also transfers the SDK's generic lowercase names into future application and dependency code. Nothing in this evidence requires that wider compatibility policy change.

**A narrower call-site/header-order workaround is insufficient.** Loading shell/COM and iphlpapi before cleanup can repair eager parsing for those files, but does not repair deferred Winsock FD expansion. Temporarily defining lowercase macros around each use is fragile and leaves the independent shell boundary. Reimplementing FD macros changes SDK-owned behavior and still leaves shell parsing. A shared helper could express A once, but adding another header/include mechanism is not needed for two small existing cleanup sites; if introduced, its include-guard behavior must not prevent a second normalization after a later header changes macro state.

**Late header redefinition remains a falsifiable caveat.** The captured SDK snippets prove the observed aliases, not that every possible Windows or third-party header avoids raw lowercase `far`/`near`, or avoids subsequently rebinding uppercase aliases/redefining lowercase names. A late raw-lowercase annotation would be a counterexample to A at that include boundary. A header that recreates lowercase macros would instead break identifier preservation. Do not claim arbitrary SDK-header closure from this design. Check the actual supported include sequences and final macro state, and treat a discovered additional boundary as evidence to revisit the design. Do not add speculative cleanup of other SDK macros.

## Qualification that changes the decision

Use the same final native recipe for baseline and candidate, with identical headers, definitions, dependency roots and compiler flags except the candidate product changes. Preserve the existing SDK-only and exact baseline controls. The established baseline signature is socket fail, shell fail, iphlpapi fail, identifier pass; a candidate must pass all four. Both cl and clang-cl supplied useful independent preprocessor/compiler coverage in the original campaign. The single-token retention variants remain useful historical cause controls; they are not substitute acceptance candidates.

The most useful additional invariant controls are small combinations of the same real SDK operations:

- Run actual FD_ZERO, FD_SET and FD_ISSET after the late shell/COM and iphlpapi includes as well as immediately after compat. Include legitimate lowercase identifier declarations/uses after those headers. Record uppercase expansion and lowercase definedness at both points. This rejects a header-order workaround that only passes the original separated cases.
- Cover native SDK-first then compat and compat then late SDK orders. For the second cleanup site, cover posix_extra first and posix_extra then compat using the actual supported compiler/include environment. Verify FD_SETSIZE separately if that forced-include order imports Winsock before ordinary compat's 1024 definition; do not accidentally claim this unrelated preexisting ordering property was repaired.
- Preserve the legitimate identifier behavior. A candidate that merely retains lowercase macros must fail that control. A candidate that normalizes only FAR must still be caught by shell's independently demonstrated NEAR requirement. These are plausible incomplete implementations that a socket-only test would accept.

Real production compilation is a separate gate from the component matrix. Compile the unmodified complete `src/util/sock.cpp`, `src/common/args.cpp` and `src/common/netif.cpp` before/after using the applicable Windows configuration and genuine dependency/generated headers. Those are the three source-backed failing boundaries. Do not replace them with extracted functions, omit their Windows branch, introduce private modelnet forced includes into them, or label preprocessing alone as compilation. Retain actual commands, source/header hashes and exact diagnostics. A baseline failure must reach the demonstrated macro cause; an earlier missing dependency is a setup failure, not the before half of the repair proof.

For actual identifier preservation, `src/net_processing.cpp` is the ordinary production witness and should be compiled if dependency closure permits. For a two-header patch, modelnet `swarm_execnbhd/seating.cpp` covers both lowercase identifiers and `swarm_lifecycle.cpp` plus its real header covers the parameter spelling; use the actual target's forced include. They add meaningful qualification, not a new functional campaign. If unrelated existing portability/dependency failures prevent completion, preserve those diagnostics and explicitly narrow the acceptance claim; neither synthetic controls nor a shimmed source extraction turn such a result into full-TU success.

## Supported-platform interpretation

The current source documents native MSVC and MinGW cross builds (`CMakeLists.txt:416–440`) and provides an explicit clang-cl static preset (`CMakePresets.json:37–55`). The existing native campaign is SDK 10.0.26100.0, x64 Windows Server 2025, cl toolset 14.51.36231 and clang-cl 20.1.8. A normal flat Win32/Win64 SDK uses these obsolete pointer-distance annotations as empty macros; this review independently confirms that fact only for the captured installed SDK. A MinGW claim needs its own installed headers/compiler/compile result or a clearly stated source-only limitation. No 16-bit segmented-pointer target is evidenced or qualified by this repository configuration, and A must not be described as a generic segmented-memory repair.

The path name `compat/mingw` does not make posix_extra a MinGW-only concern: its source guard is `_WIN32` and its CMake force-include condition is `WIN32`. Its existing `-include` option and POSIX dependencies are separate native-toolchain concerns; this review does not establish that the complete modelnet target builds with cl or clang-cl. Do not silently repair those unrelated concerns or report modelnet closure from a macro-only probe. Likewise, the ordinary three TUs inherit `core_interface` but not modelnet's PRIVATE force include. Their successful compilation proves that actual selected boundary, not linking, runtime behavior, a complete node, GPU/model execution or release readiness.

## Disposition

Design verdict: **A is the smallest coherent repair candidate, provided both existing cleanup sites preserve the uppercase meaning and validation establishes the actual claimed include boundaries.** B is a wider alternative if a real supported-header counterexample defeats A; there is no present evidence requiring it. No unresolved native test is represented as passed here. Parent owns candidate selection, before/after execution, final artifact review and shared-ledger closeout. No upstream posting is authorized. Reviewer output is complete and reviewer resources are released.
