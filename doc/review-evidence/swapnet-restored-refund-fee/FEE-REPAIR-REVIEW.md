## Amount conversion can round before validating exactness

`candidate/swapnet/drivers.py:297–303` multiplies Decimal(value) in a context with precision100, then tests whether the result is integral. A supplied decimal value with more than100 significant digits can lose a tiny fractional-atom tail during multiplication; testing the rounded result then accepts an amount that was not exactly integral in the original response. For example, construct a coin fee representing one atom plus a fractional-atom tail beyond the100-digit precision. The original value is not atom-exact, but arithmetic can round it to exactly one atom. This violates the proposed strict Decimal/no-guess fee provenance rule. The configured RPC JSON/string surface can represent such a value; successful normal8-decimal node output alone does not prove this refusal control.

Small repair direction: establish finiteness/range and exact integer scaling from the original Decimal coefficient/exponent, or use arithmetic precision derived from a tightly bounded validated representation. Do not merely increase fixed precision. Require a malformed long-precision fractional-atom control to receive a classified refusal with zero replacement effects. No generic parser rewrite outside this reader is required.

This is expected malformed provider data, not an unrelated programmer exception. It breaks the explicit classified fail-closed response contract, although replacement signing/persistence still has not occurred at this point.

Use precise expected decimal exception handling/early finite exponent/range validation. Preserve real typed transport errors as supplied; do not blanket-catch Exception. Include huge-exponent/NaN/infinity/negative/fractional/missing fee controls and verify both classified errors and unchanged original refund/operations/budgets. This is a bounded parser/refusal qualification, not a new native gate.

The new helper also uses `to_atoms(output.get('value'))` at line287 and `decoderawtransaction(...).get` at line290 without normalizing malformed data responses. If these fields are in the promised malformed-response contract, require focused controls for invalid output amount and non-object decoder reply: expected external data errors should be classified rather than become bare InvalidOperation/AttributeError. Avoid masking programmer errors elsewhere.

## Canonicality: direct and hinted lookup differ

`candidate/swapnet/drivers.py:258–264,279–303` accepts a direct verbosity2 response containing fee without validating its blockhash/header or in_active_chain fields. Only the wallet-hinted branch checks current block-header confirmations at lines271–273. `fee_bump.py:24` rejects conflicting observations but does not require the report to be present/exact/canonical; those are distinct LegObservation fields. Consequently fresh `observe` invocation alone is not proof that the newly resolved historical original is canonical.

The agreed design called for current canonical-original validation. Either validate the available direct transaction block identity/canonicality on the new historical path (and retain current maturity/conflict checks), or explicitly narrow/discharge this design requirement with a supported rationale. The exact fee is a property of an immutable transaction even after a reorg, so this source gap is not by itself proof of fee undercount or funds loss. Do not silently imply that the direct route checked canonicality; do not broaden ordinary/EVM spending policy to resolve this one review point.
