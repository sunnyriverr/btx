## Original findings and rationale

The references in this section identify the initial reviewed version; the dispositions above identify the revised source.

1. **P1 — extraction and directory-mode assertion disagree under the private umask.** `accept.py:122` uses `tar.extractall(..., filter='data')`. Python's data extraction filter clears directory mode metadata, so newly extracted directories use the creating process's umask. `workflow.yml:98` selects umask 077; the producer manifest pins directories such as `bin` to 0o755 (`pins/members.json:2-5`). `accept.py:128` then requires every extracted directory mode to equal that original value. This is expected to reject the exact valid archive before installation. Validate tar metadata against the producer manifest before extraction, and explicitly restore admitted directory modes or keep filtered-extraction expectations distinct from original archive metadata. This is source reasoning, not a reproduced runtime result.

2. **P2 — timeout containment can lose the GUI's host descendants and cuts ordinary cleanup short.** `accept.py:72-78` grants only ten seconds between TERM and KILL. `lifecycle.py:253-259` can spend thirty seconds waiting for ordinary stop, and its review explicitly calls for at least sixty seconds of parent grace. `gui.py` installs no TERM/INT handler and launches each application in a separate session (`gui.py:103-109`). Consequently controller timeout can kill the GUI driver without running its finally cleanup; the parent fallback scans only executables inside the prefix (`accept.py:48-61,202-213`), missing surviving host WebKit children. Give both drivers an interrupt-to-failure cleanup path and adequate bounded grace, and preserve sufficient ownership information or an encompassing process scope for parent containment if a child cannot finish cleanup. Any timeout must continue to fail acceptance.

3. **P2 — the member metadata check does not verify the retained link contract it claims to retain.** `accept.py:107-134` validates allowed tar entry types, then compares a filesystem snapshot. That snapshot collapses regular files and hardlinks; size is not compared. The actual manifest's `libexec/btx-guardd.real` is a hardlink with `target`, `link_text_sha256`, and archive size zero (`pins/members.json:5249-5255`), but these fields are ignored. The symlink branch uses `want['linkname']`, while the observed link schema uses `target`. Validate each original TarInfo entry against its manifest type/mode/size/hash and link fields before extraction; retain separate filesystem checks for installed bytes. The exact outer and inner digest already bind the archive bytes, so this is an incomplete claimed structural assertion rather than evidence of an admitted substituted artifact. The exact upstream `cp -RP` installation does not promise retained hardlink inode topology; do not change that product routine to manufacture such a promise.
