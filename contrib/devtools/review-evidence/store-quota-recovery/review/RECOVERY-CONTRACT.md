## Verdict

**Reject “the 16,384-object cap blocks all safe containment.”** At this object-count limit, the supported local owner pause remains structurally available, and a fresh directly supplied owner-signed resume control also avoids object insertion. Pause can remain set across guard restart. These are containment/re-authorization operations, **not recovery of storage capacity or continuous evidence renewal**.

**No general supported path was found to apply a new revocation notice or install a new policy at the cap without making object capacity available.** Offline CLI paths use the same quota-enforcing functions. The known quota failures are JPP's #275 finding 1 (comment 6433856983), not a new finding. Neither manual SQL deletion nor a fresh empty security directory is an established safe recovery ceremony.

All availability conclusions here assume a usable/writable SQLite database, a nonrollback operation timestamp, valid resume authority where applicable, and prompt completion within the real IPC budget. An object count alone proves none of those conditions. Actual owner-RPC pause/resume timing at the cap is unexecuted.

## Supported control and persistence paths

- `database.cpp:162–189`: `Put` rejects a **new ID** when `count(objects) >= 16384`; an existing ID may merge signatures. The cap is not a global SQL-write prohibition. Metadata, permits, revoked subjects, replay controls and journal are separate tables (`database.cpp:60–78`). No `DELETE FROM objects` or configurable object-cap operation was found in security-v2.
- `broker.cpp:522–528`: `Pause` begins a transaction, checks the saved monotonic clock, sets `paused=1`, marks prepared/executing permits revoked, appends an event and commits. It calls no `Put`, loads no policy and requires no signed pause envelope. It can therefore contain the broker even when policy authority itself has expired, provided the clock/database operations succeed.
- Permissions come from the owner interface: `Service::Handle` dispatches `{"op":"pause"}` directly (`service.cpp:473–478`). This is the documented owner RPC, not a peer RPC (`rpc/modelnet.cpp:2427–2453`, `doc/modelnet/security/OPERATIONS.md:35–39`, `PROTOCOL.md:42–50,66–73`). Do not invent a second signed pause requirement or treat this as a public unauthenticated network control. The security-v2 service itself assumes that owner transport boundary; it does not implement another per-request identity role for pause.
- `broker.cpp:530–555`: `Resume` verifies current policy, an unrevoked owner signature, realm/epoch, operation `resume`, a 32-byte nonce and a valid lifetime no longer than 60 seconds. It consumes `RecordId(e)` in `consumed_controls`, clears pause and journals in one transaction. It **does not import/store the control in `objects`**. Requiring an `import` before `resume` would invent an unnecessary quota-dependent prerequisite.
- `broker.cpp:295` checks pause before grant admission. Existing execution rechecks authorization before effect, in the worker callback, before dispatch return and before durable completion/release (`broker.cpp:356,409,451–493`). `CanRelease` uses the same authorization (`512–520`); an async private-output `take` rechecks it (`service.cpp:358–366`). Evaluation/canary/remote-work callbacks also check pause (`evaluation.cpp:167–178,243–255`, `work.cpp:57–67`). This is forward-looking scoped containment; already completed external effects/plaintext cannot be recalled (`ARCHITECTURE.md:43–57`).
- Resume does not restore revoked permit phases. Do not overclaim that every previously completed queued result is permanently destroyed by pause: `Take` checks current grant authority, and pause changes only prepared/executing permit phases. The durable permit replay guard remains `broker.cpp:425–428`.
- Guard startup writes a fresh boot, runtime availability, permit revocations, interrupted job/evaluation phases and `guard-started` in one transaction (`service.cpp:77–86`). It does **not** clear `paused`. Shutdown attempts runtime unavailable + permit revocation + `guard-stopping` transaction; failures are swallowed (`103–114`). Object quota alone does not obstruct these writes; full database storage may.
- The supervisor closes/kills the child on failure and retries while enabled (`guard_supervisor.cpp:121–153,349–360`); explicit `Stop` disables retry (`363–367`). Merely killing an enabled guard is not a durable pause. A partial frame failure loses ephemeral output and invalidates boot-bound outstanding permits on restart (`433–438`). Guard `Service` construction must succeed before stdio is usable (`btx-guardd.cpp:27–37`).
- Pause is not a global maintenance/storage freeze. `Maintain` calls `MeshTick` and lifecycle before its pause checks for new evaluation/work (`service.cpp:242–250,294–297`). It does not reclaim object slots; mesh creation can continue/fail while paused, and a quota exception can still skip the later lifecycle call. Do not equate a successful pause with restored continuous protection.

## Why new authority still has no general recovery route

`InstallPolicy` verifies pinned roots, new same-realm increasing epoch and existing owner signature, then calls `Put` before advancing policy metadata (`trust.cpp:134–153`). `ImportRecord` validates revocation authority using the revoker role and release threshold (`246–254`), then wraps clock, `Put`, `Revoke`, permit invalidation and journal in one transaction (`382–409`). The CLI `install-policy`/`import` calls these same functions (`main.cpp:148–157`); `request` constructs the same Service and requires the active guard to be stopped (`main.cpp:54,169–174`). There is no exposed quota-increase/prune/revocation-only recovery operation.

Existing-ID exceptions do not supply a general escape: a newly issued revocation/policy has a new body ID. A previously imported revocation normally already has its revoked-subject row because both were committed atomically. Reinstalling the current policy is rejected by the increasing-epoch rule. Signature merging does not turn an old body into a new policy epoch or revocation subject.

**Broken fix to reject:** move `db.Revoke` above `db.Put`, leaving the same transaction. `Put` still throws `SEC_OBJECT_QUOTA`; the transaction destructor rolls back (`database.cpp:131–143`), including the earlier `Revoke`. Moving it outside the transaction or swallowing the failure instead creates a different policy: local negative authority without its durable signed notice and atomic audit/import completion. That needs an explicit recovery design, not just statement reordering. It also does not repair policy installation, fresh evidence admission, or SQLite page/disk exhaustion.

## Object cap versus actual storage exhaustion

`database.cpp:56–59` selects WAL/FULL sync, autocheckpoint 128 and `max_page_count=131072`. The page-count ceiling is separate from `count(objects)` and must not be described as a 16,384-record total-database ceiling or an assured fixed byte limit without page-size evidence. WAL growth and filesystem free space are further distinct limits; these lines do not impose a WAL byte cap. Journal inserts and metadata writes remain capable of failing even though they bypass `Put`.

Pause and resume both append journal events. If page/disk exhaustion makes those writes fail, transaction rollback prevents claiming that pause/resume persisted. Startup also appends `guard-started` before serving requests. JPP's separate finding 4 already reports guard-start failure at page exhaustion. Do not repeat that result as new evidence, or infer object-quota pause failure from it. `Query` maps nonbusy SQLite step errors to `SEC_DATABASE_WRITE` (`database.cpp:125`); that generic code does not itself identify page cap, WAL pressure or disk-full cause. IPC additionally has a 500 ms exchange budget (`guard_supervisor.cpp:36,154–157`), so source permission is not a runtime latency qualification.

## Retention and recovery constraints

1. Preserve the metadata journal and reviewed evidence as the operator guide requires (`OPERATIONS.md:35–39`). Journal verification starts from the all-zero predecessor and ends at `meta.journal_head` (`database.cpp:215–244`); arbitrary event prefix deletion breaks this contract. Archival/checkpoint semantics need an explicit verifier/migration design.
2. Never age-delete all evaluations. `AdmitCapsule` intentionally scans **all retained** FAIL reports; a report valid under current evaluator policy remains negative evidence even after its positive freshness window (`trust.cpp:438–447`; `ARCHITECTURE.md:66–70`). A cleanup that deletes old FAILs can convert a denied candidate into an admitted one. Keep signed negative evidence or a deliberately specified authoritative equivalent across archive/reopen/reimport.
3. Retain complete live authority/dependency closure: active policy/root custody; grants; active/previous/candidate capsules and compositions/ancestry; mandates/update records; referenced evaluations/challenges/receipts and canary observations. Policy load uses `objects[active_policy]` (`trust.cpp:103–112`); admission dereferences composition/evaluation/challenge/receipt (`413,427,455–503`); lifecycle activation and rollback dereference mandates, updates, observations and predecessor admission (`lifecycle.cpp:156–223`). Deleting “expired” evidence without checking retained predecessor needs can break rollback.
4. Preserve permanent safety/replay/budget state independently of ordinary evidence TTL: revoked subjects/epochs (`database.cpp:246–257`, no expiry), ancestry quarantine (`279–294`), policy epoch and saved clock, consumed resume/enrollment controls, permits and cumulative grant budgets (`broker.cpp:425–449,547–552`), trials (`trust.cpp:394–403`) and evaluation/work/round attempt records (`evaluation.cpp:154–165`, `work.cpp:49–55`, `mesh.cpp:243,257`). A new database or naive deletion can reopen authority/replay/budgets; that is not safe generic quota recovery.
5. The export dependency helper is useful input, not a complete garbage-collection root set: `peer.cpp:89–101` lists composition/capsule/receipt/challenge, capsule evaluations and composition parents. Lifecycle state, policies, grants, campaigns/work linkage and negative history add roots beyond that helper. Mesh freshness selects the newest challenge and scans reports (`mesh.cpp:318–333`); mesh/peer outboxes and in-flight dependencies also need deliberate retention handling.

## Smallest worthwhile untested observation and policy decisions

Prior source coverage already includes ordinary pause/resume permit replay (`test/util/model_security/security_tests.cpp:154–156`) and real-daemon owner-RPC pause surviving node/guard restart (`test/functional/feature_model_security_v2.py:28–53`), with no installed policy and no full-store boundary. These are existing supplied tests, not executions performed in this review. Repeating them unchanged adds no quota evidence.

If a later resource/ownership gate permits execution, extend the existing quota fixture with one **synchronous Broker/database containment sequence**, without worker launch: prepare an ordinary permit under valid authority; reach exactly 16,384 objects while keeping SQLite writable; call Pause; verify unchanged object count, `paused=1`, revoked permit phase and `CanRelease=false`; reopen the database and verify pause persists; supply a fresh owner-signed resume directly (without import), verify success and unchanged count, reject replay, and verify the old permit is still unusable. A below-cap valid control distinguishes fixture/clock/authority failure. This would establish a presently source-only containment boundary, not rediscover JPP's import failure. Service/owner-RPC transport and guard-boot timing remain separate untested integration claims. No such execution is authorized/selected by this report, and current host space is below the required reserve.

The smallest integration delta, if an actual restart decision remains necessary, is to extend the existing functional owner-RPC pause/restart case at exactly the object cap: use valid installed authority and a prepared harmless permit; establish writable nonfull SQLite storage and the exact 16,384 count; pause through `modelsecurity`; restart the owned node/guard; require a new `guard_boot`, persistent `paused=true`, valid journal, unchanged object count and denial of the old permit; then submit a fresh signed resume directly and require the same count plus persistent old-permit denial and resume-replay refusal. Capture pause response latency and distinguish transport timeout/database error from quota error. Use the existing below-cap sequence as the legitimate control, not another large matrix or repeated JPP import reproduction. A broken implementation that stores a pause/resume control using `Put` passes ordinary tests but fails the cap phase; a broken startup that clears pause passes a database-reopen-only probe but fails the actual guard restart observation. Synchronous component success alone must not be labeled Service/daemon restart proof. This is a future contract only; no runtime is selected while below the disk reserve.

Before a repair is selected, the author must choose: (a) guaranteed emergency capacity versus a separate bounded authority/revocation store; (b) how a negative-authority decision and its signed notice/audit are committed together; (c) what negative-history/closure may be archived and how deny semantics survive reopen and reimport; (d) whether exhaustion mandates a persistent paused state and what exact authority clears it; (e) recovery when the physical database cannot append even a pause/start event; and (f) bounded journal verification/IPC latency. Root/expired-policy recovery is explicitly not implemented (`OPERATIONS.md:16–20`), so no blanket “resume always recovers” claim is warranted.
